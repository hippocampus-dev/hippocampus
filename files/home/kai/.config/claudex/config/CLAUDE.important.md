## Important

会話や `Plan` は日本語で行いつつも、ドキュメントやコードコメントは英語で書く必要があります。
会話は直訳調を避け、レビュー結果や英語のルールにある語をそのまま訳して持ち込まず、読み手が普段使う語彙で書いてください。
コード内の識別子やファイル内の呼び名、読み手が調べないと分からない語、自分がその場で作った言い方、ありふれた語をその場かぎりの呼び名にしたもののように、読み手がそのレスポンスの中でまだ見ていないものを指す語は、その指す先の実物(実際に出力された文字列、ファイルのその行、コマンドの出力)を先に見せ、読み手の言葉で一言添えてから使ってください。
指示語や接続語で、読み手がそのレスポンスの中でまだ読んでいない文を受けないでください。
自分が前に書いた文や別のファイルの文をそのまま引いて説明の土台にすることも同じで、説明の対象がその文自体である場合も変わりません。
ファイルパスはすべて絶対パスで出力してください。
レスポンスは結論を先に書き、原因や見通しが確定していないことも結論に含めて先に書き、根拠や経緯はその後に続けてください。
これから行う調査や操作を告げるだけの文、どう調べたかの手順、既に書いた内容の言い換え、結論を支えない調査結果は書かないでください。
並ぶ項目や分岐が3つ以上あるときは、散文で連ねずに表にしてください。
前提の訂正や自己修正は、読み手の判断を変えるものだけをまず結論を示してから述べ、判断を変えないものは宣言せず本文に反映するだけにしてください。
変更やルールを説明するときの結論は、それが無いと何が起きるかで、その出来事は読み手が目にする形(何がどこに出て、何が出ないか)で書いてください。

ファイルの作成・変更を伴う作業では、必ず `TaskCreate` を使用してタスクを計画してください。
`TodoWrite` が使える環境では、`TaskCreate` の代わりにそれを使ってもかまいません。
また、タスク作成の際には必ず以下をリストのしかるべき箇所に追加しなければなりません。

| 項目 | タイミング | 回数 | 内容 | 再実行の理由としないもの |
|------|-----------|------|------|------------------------|
| 準拠 | 最初 | - | 関連性の高い既存のファイルを3つ以上探し、見つかったファイルの構造・命名規則・処理の順番などあらゆる観点で徹底的に準拠するようにする | - |
| 棚卸し | 作業を終えてユーザに返す直前、変更サマリを作成する前 | 同じ対象への一連の作業につき1回 | 追加した記述をコード・設定・コメント・ドキュメント・ルールの区別なく1件ずつ挙げ、それぞれに適用されるルールと `## General` の基準で要否を判定する | 削った結果、同じ対象への指示が続いたこと |
| 並列: レビュー | その作業を終えてユーザに返す直前 | 同じ対象への一連の作業につき1回 | 前のバッチにまだ返っていないエージェントが残っていればそれだけを止め、検証の済んでいない作業も含めて現在の状態で変更サマリ(変更ファイル・変更内容・変更理由・影響範囲・作成した一時ファイル・ユーザから指摘された内容・追加した記述とそれを残すと判断した根拠)を作成し、配下で利用するエージェントをすべてまとめてbackgroundで起動して変更サマリだけを渡す | 指摘を反映した変更、同じ対象への指示が続いたこと |

`並列: レビュー` が配下で利用するエージェントは以下です:
- (実装タスクのみ)@verification エージェントを利用
- (実装タスクのみ)@final-review エージェントを利用
- @documentation-review エージェントを利用
- @rules-review エージェントを利用

作業ではリポジトリ内での一貫性と処理の対称性を何よりも優先してください。
いかなる時でも、やると決めた対応は最小限の差分で実現することを心がけ、ファイルの種類ごとに適用されるルールに必ず従ってください。
ファイルの作成・変更は、シェルからの書き換えでは対象パスに紐づくルールもフックも起動しないため、内容を自分で書くものはファイル編集用のツールで行い、生成コマンドが作る出力はそのコマンドの実行で更新してください。
あなたはSandbox環境で実行されており、Working Directoryと `/tmp` 以外は読み取り専用です。
`.git` も読み取り専用なので `git commit` などは行えません。
Working Directoryは並行して動く他のセッションと共有され、どのセッションもcommitできないため、`git diff` や `git status` が返す未コミット変更には他セッションのものが混じり、自分が変更した範囲の特定には使えません。
どのセッションもcommitできない以上、上書きした未コミット変更を戻せるコミットはどこにもないため、追跡ファイルをコミット済みの内容から作り直して自分の変更だけを載せ直してはなりません。
サンドボックスの制限で仕事をしないまま終わるコマンドがあるので(`ping` は `cap_set_proc` に失敗し、`ip` と `ss` はnetlinkソケットを開けず、`avahi-browse` はD-Busに繋げません)、到達性や存在の有無を判定するコマンドは標準エラー出力を捨てず、終了ステータスで起動できたことを確かめてください。
`systemctl` は `/run/systemd/system` が見えず `System has not been booted with systemd as init system (PID 1). Can't operate.` を返すので、ユニットの状態や失敗は `journalctl` から読んでください。
ただしKubernetes環境への権限は適切に付与されています。
