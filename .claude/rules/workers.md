* Next.js on Cloudflare Workers via opennextjs-cloudflare
* Local development (`npm run dev`) supports all Cloudflare bindings (KV, R2, AI) via remote bindings
* Do NOT suggest `npm run preview` for binding access - `npm run dev` works
* Do NOT use `getCloudflareContext` directly in route handlers or Server Components
* Place reusable components in `components/` (not co-located with route segments in `app/`)
* Uses shadcn/ui components in `components/ui/`
* Use `custom-worker.ts` only to re-export Durable Objects / `WorkerEntrypoint` classes that the Next.js handler cannot expose directly
* `custom-worker.ts` (entry importing `.open-next/worker.js`) must be listed in `tsconfig.json` `exclude` — the import target is generated by opennextjs-cloudflare build
* Name the request-interception file `middleware.ts` and never add the `proxy.ts` convention that supersedes it — `proxy.ts` compiles to Node.js middleware, which `opennextjs-cloudflare build` rejects with "Node.js middleware is not currently supported"
* Weigh every `source` lookahead exclusion in the `middleware.ts` matcher against the `/[id]` route before taking it from the Next.js CSP guide — the lookahead runs as raw regex at the single position after the leading `/`, so an exclusion a paste id can start with drops that page and it ships with no CSP header at all; keep the guide's spelling only where the literal cannot be an id, because it carries a `/` or outruns the length `ID_PATTERN` in `lib/storage/cloudflare.ts` fixes, an unescaped `.` matching an id character all the same
* Do not count on the `has`/`missing` conditions of a `middleware.ts` matcher — `getMiddlewareMatch` in `@opennextjs/aws` keeps only each matcher's `regexp` and `handleMiddleware` tests that against the path alone, so the Next.js CSP guide's prefetch exclusion holds under `next dev` and drops out of the deployed Worker
* Leave every route dynamically rendered, PPR and ISR included — Next.js stamps the CSP nonce only while server-rendering a request, so prerendered HTML ships script tags carrying no nonce and cached HTML ships one from an earlier request, and `'strict-dynamic'` voids the `'self'` that would otherwise admit them
* Do not take `experimental.sri` for the nonce-free alternative the Next.js CSP guide advertises — Next.js leaves `integrity` off the per-route client chunks it emits from the client reference manifest, and the RSC payload it inlines as `<script>` has no build-time hash at all
* Outbound `fetch()` from route handlers may forward `request.signal` so client disconnect closes the downstream connection; do NOT add `signal` plumbing to wrappers around `env.AI.run()` / `WorkerLoader` entrypoints — these bindings do not accept `AbortSignal` and `Promise.race` only changes when the handler returns, not when the work stops

## Abstraction Layer

Use Repository pattern for storage, Provider pattern for AI, and Runner pattern for code execution.

| Context | Pattern |
|---------|---------|
| Route handlers / Server Components | `await get*()` factory functions from `lib/` |
| Custom workers (direct env access) | Import `Cloudflare*` classes from `lib/*/cloudflare` |

Factory functions are async and use `getCloudflareContext({ async: true })` internally for SSR/SSG compatibility.

## Storage

| Storage | When to Use |
|---------|-------------|
| KV | Small data (<25MB), fast reads, TTL support |
| R2 | Large content, binary data |

## Dynamic Worker

Passing tail handlers to `WorkerLoader.get({ tails: [...] })`:

| Target | Use |
|--------|-----|
| Tail handler class | `export class X extends WorkerEntrypoint<Env, Props>` implementing `tail(events: TraceItem[])` |
| `tails` array element | `ctx.exports.X({ props: {...} })` — NOT a DO stub |

Retrieve the factory via `(ctx as { exports?: {...} }).exports?.X` from `getCloudflareContext({ async: true })`.
