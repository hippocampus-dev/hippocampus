* Relay the SIGTERM `bin/runner.go` receives to its `run.sh` child and bound the wait for that child's exit below the `TerminationGracePeriodSeconds` `buildDeployment` sets - the kubelet signals PID 1 only, which is this binary wherever the container leaves in place the `ENTRYPOINT` the Dockerfile `image.WorkspaceConfigMap` renders declares, as `RunnerReconciler.buildRunnerContainer` does and `ScaleSetReconciler.buildRunnerContainer` does not, so a relay left out or a wait left unbounded ends in SIGKILL with `config.sh remove` never reached and the runner left registered as Offline on GitHub while the pod deletion, the Deployment and the Runner CR all report success
* Keep the token secret's `expiresAt` out of the Pod template `buildDeployment` renders - `RunnerReconciler.buildRunnerContainer` passes `--token` as the path of that mounted Secret and `getRemoveToken` in `bin/runner.go` re-reads the path at shutdown, so stamping the expiry on the template only rolls the Deployment at every renewal and drops whatever job each runner holds; `github-actions-exporter-controller` keeps that annotation because `cluster/applications/github-actions-exporter/main.go` reads its token file once in `main` and nothing but a restart picks up a new one
* Keep `tokenRefreshMargin` wider than the kubelet's `syncFrequency` plus the delay its `configMapAndSecretChangeDetectionStrategy` selects (`kubectl get --raw /api/v1/nodes/{node}/proxy/configz` reports both running values) - nothing rolls the Pod on renewal once the expiry is off the template, so a narrower margin opens a gap between the old token expiring and its replacement reaching the mount, and a shutdown landing in that gap hands `config.sh remove` an expired token and leaves the runner registered while the pod deletion, the Deployment and the Runner CR all report success
* Keep `runnerLabel` in every list `RunnerReconciler.runnerLabels` and `ScaleSetReconciler.scaleSetLabels` return, and `selfHostedLabel` in the latter, whatever `spec.labels` holds - a job runs only where every label its `runs-on:` array names is registered, and every `Runner` and `ScaleSet` `cluster/manifests/runner/base/kustomization.yaml` deploys registers the pair `## Runner Selection` in `.claude/rules/.github/workflows.md` sends to cluster internal access, so one list losing a label moves every such job onto the workloads whose list still carries it and every list losing it leaves them queued with no runner to take them, with the CRs, their workloads and their pods reporting success either way; `config.sh` registers `self-hosted` for `Runner` on its own and GitHub adds it to no scale set (https://github.com/actions/actions-runner-controller/issues/3330), which is why only `ScaleSetReconciler.scaleSetLabels` puts it in the list it returns
* Pass a flag `bin/runner.go` gained to the runner container only when the CR field it serves is set, until `main.go`'s `binary-version` default names a release carrying it - `image.WorkspaceConfigMap` renders a Dockerfile that `ADD`s the runner binary from the release named by `BINARY_VERSION` instead of building it from this tree, so an unconditional flag reaches a binary whose release was cut before the flag existed, and its `flag.Parse` exits 2 on the unknown flag and puts every runner pod into CrashLoopBackOff while the Runner CR and its Deployment both report success
* Reset `Status.DesiredRunners` to `min(spec.MaxRunners, spec.MinRunners)` in the same status write that records `ScaleSetID`, whenever `runnable.ScaleSetListener.Running` reports no session for the current generation - `reconcileRunners` creates the difference between the runner Jobs it counts and that field and deletes nothing, so a count outliving the session that produced it (a controller restart, or any `spec` edit, since `runnable.ScaleSetListener.Ensure` retires the handle on a `Generation` change) becomes that many runner Jobs no later report takes back while the ScaleSet CR, its Jobs and their pods all report success; `Status.ScaleSetID` crosses the same boundary on purpose, since `finalize` reads it to unregister a scale set whose listener is gone
* Remove the runner from GitHub before `deleteOrphanedJitConfigSecrets` deletes the secret that holds its JIT config - GitHub de-registers an ephemeral runner only once it has processed a job, and `createRunner` keeps no identifier but the name it gave both, so a reaper that drops the secret first leaves the runner registered as Offline with nothing left to unregister it by, while the ScaleSet CR, its Jobs and the reconcile all report success
* Pass a generated pod only the volumes the containers that pod runs mount, filtering `spec.template.spec.volumes` through `filterMountedVolumes` as `buildBuilderVolumes` and `buildRunnerVolumes` do - `pods.validating.kaidotio.github.io` in `cluster/manifests/validating-admission/base/validating_admission_policy.yaml` sums the mount lists of a pod's initContainers and containers and rejects a pod holding a volume none of them names, and `ScaleSetReconciler` splits that one field across a build Job whose kaniko container mounts what `builderContainerSpec.volumeMounts` names and a runner Job whose runner container mounts what `runnerContainerSpec.volumeMounts` names, so a volume the receiving pod leaves unmounted gets that pod denied while the ScaleSet CR, its Job and the reconcile all report success; `RunnerReconciler.buildDeployment` needs no such filter only because its kaniko initContainer shares the pod with the runner container, so pass every container a generated pod gains to the same filter rather than reading one container's mounts
